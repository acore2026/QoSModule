free6gc adaptive_qos / implementation comparison

当前实现与方案A，到底差在哪里？

两种方案都能支持“MASQUE请求 → QoS计算 → RAN下发 → UDP回包”， 但当前实现把共享模块和新协议接入了free6gc核心路径；方案A则把新能力限制在一个默认关闭的旁路处理器中。

RECOMMENDATION 如果目标是快速同步到free6gc代码库，方案A更合适。

它牺牲少量代码复用，换取原算法零改动、数据面零改动、默认行为零变化和更简单的构建部署。

≈ 12 方案A预计修改 adaptive_qos.go 行数

04 / Code path

代码层面具体发生了什么

当前实现修改多个既有函数；方案A只在reportLoop加一个受控分支，匹配失败后立即回到原代码。

当前实现 / reportLoop 每个report先尝试新协议 
c.counters.reportsReceived.Add(1)

if result, handled :=
    c.processProjectQoSPayload(
        context.Background(),
        buf[:n],
    ); handled {
    // 统计、回包、continue
}

// 原AdaptiveReport流程
var report AdaptiveReport
json.Unmarshal(buf[:n], &report)
方案A / reportLoop 默认关闭 + 严格旁路 
c.counters.reportsReceived.Add(1)

if c.cfg.ProjectRANQoS != nil &&
    c.cfg.ProjectRANQoS.Enable {
    if result, handled :=
        c.tryHandleProjectRANQoS(
            context.Background(),
            buf[:n],
        ); handled {
        // 回包、continue
    }
}

// 以下原代码逐行保持不变
var report AdaptiveReport
json.Unmarshal(buf[:n], &report)

07 / Migration path

从当前实现迁移到方案A

迁移目标不是删除当前独立target或共享模块，而是让ref/free6gc恢复最小侵入。 `adaptiveqos` 仍可继续服务独立target和其他项目。

01

恢复原策略

将derivePredictiveBurstDecision和rateFromBurst恢复为free6gc原实现。

02

移除热路径分支

删除InterceptUplink中的新协议识别和异步goroutine。

03

解除构建耦合

从go.mod删除adaptive-qos require与本地replace。

04

加入受控旁路

reportLoop仅增加默认关闭、严格匹配的tryHandle调用。

05

新增自包含文件

将请求解析、公式、裁剪和RAN HTTP集中到adaptive_qos_ran.go。

FINAL DECISION

方案A是验证期的更优边界

  • 可以直接形成free6gc仓库内的独立patch
  • 默认关闭，不改变现有部署行为
  • 原AdaptiveReport、Session和QER代码不动
  • 不在UPF用户面数据路径加入控制逻辑
  • 不依赖外部目录和本地replace
  • 后续模块正式发布后仍可再次收敛重复代码
